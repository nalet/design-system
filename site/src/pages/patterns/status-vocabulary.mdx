# status vocabulary

One status per object, said once, in the object's own words, from one table — the same everywhere the object appears.

<Example label="a backlog's vocabulary" column>
  <StatusCell {...BACKLOG.wanted} detail="nothing found · again in 6h" />
  <StatusCell {...BACKLOG.queued} detail="queued for a search and grab" />
  <StatusCell {...BACKLOG.failed} detail="the release was removed by its source before it finished" />
  <StatusCell {...BACKLOG.held} />
</Example>

## when to use

- Every list, row, card or page that shows the state of things: items in a backlog, hosts, jobs, sources, downloads.
- Before building the screen: the vocabulary decides the tabs, the counts, the toasts and the empty states.

## when not to use

- **A label, a tag or a count** that is not a state → <C slug="badge" />.
- **A condition of the whole page** ("105 titles can't be checked") → a <C slug="message-strip" />.
- **The result of an action just taken** ("8 episodes queued") → a <C slug="toast" />.

## anatomy

1. **The state** — one of five: neutral, information, success, warning, error. It carries the meaning and decides colour and glyph; see [colour](/design-system/styles/colour/#semantic-state) for what each means and must never mean.
2. **The text** — the state in the object's words, two or three words: `missing`, `on its way`, `needs attention`.
3. **The detail** — optional, one line: why, or what happens next: `nothing found · again in 6h`. Raw errors go behind it (on hover, or in a details disclosure), not in it.
4. **The glyph** — a shape per state (dash, bar and dot, check, triangle, cross), so the state never rests on colour.
5. **The announcement** — warnings and errors are read with their state first: "error: needs attention".

## writing a vocabulary

1. **List every value the system has**: wanted, queued, searching, grabbed, downloaded, waiting, failed, held.
2. **Group them by what the person needs to know**, not by how the system works: *missing* (nothing under way), *on its way* (something is), *needs attention* (a person must act), *held*.
3. **Give each group one state.** The words decide it: on its way is information, not success — nothing is done yet.
4. **Write the detail per raw value**: queued → `queued for a search and grab`; waiting → `waiting for the catalog`.
5. **Put it in one table** with `defineStates` and render every status from it.

```tsx
import { defineStates, StatusCell } from '@nalet/design-system';

// the one place a backlog item's state is decided.
const BACKLOG = defineStates({
  wanted:  { state: 'neutral',     text: 'missing' },
  queued:  { state: 'information', text: 'on its way' },
  grabbed: { state: 'information', text: 'on its way' },
  failed:  { state: 'error',       text: 'needs attention' },
  held:    { state: 'success',     text: 'held' },
});

<StatusCell {...BACKLOG[item.state]} detail={detailOf(item)} />
```

`defineStates` returns the table frozen, and TypeScript makes it cover every key you list. A reviewer sees in one place that "connection firewalled" is a warning.

## one status, end to end

An item reads the same wherever it shows up: the row says `on its way`, the tab that keeps it is `on their way`, its group counts it among what is on its way, and the toast after a grab says it was queued — never "success" in one place and "pending" in another. A list whose items can be in several states at once is a list whose vocabulary isn't finished.

## sorting by status

`STATE_SEVERITY` orders the states by urgency — error 4, warning 3, information 2, neutral 1, success 0 — so a status column can sort "most urgent first" with one comparator:

```tsx
compare: (a, b) => STATE_SEVERITY[statusOf(b).state] - STATE_SEVERITY[statusOf(a).state]
```

| Backlog item | `waiting` | <ObjectStatus state="information">on its way</ObjectStatus> | waiting for the catalog |
| Host | `firewalled` | <ObjectStatus state="warning">connection firewalled</ObjectStatus> | reachable only through the relay |

## do and don't

  </Dont>
</DoDont>

## keyboard and accessibility

Statuses are text, not controls: they take no focus. The glyph is decoration; the text and, for warnings and errors, the state's name are what a screen reader hears. In a table, the status cell's full detail is there for assistive tech even where the screen clamps it to two lines.
