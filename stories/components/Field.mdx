## implementation notes

- Renders a `<div>`: the label, the control, then the message.
- The control is the one child element. The field clones it with `id` and `aria-describedby`, and with `aria-invalid` and `invalid` when there is an `error`.
- The control's `id` is `htmlFor` when you pass it, else the child's own `id`, else a generated one. The field sets it on the child, so `htmlFor` wins over the child's `id`.
- The label is a native `<label for>` pointing at that `id`. Nothing transforms it: it shows the text you wrote, in the body face, so write it in sentence case.
- The message gets the ID `<control id>-desc`, which is added to any `aria-describedby` the child already has.
- With `error`, the field sets `aria-invalid` and `invalid` on the child. Without it, it leaves the child's own values alone: the control keeps whatever its own `invalid` says.
- `required` adds the ` *` marker with `aria-hidden="true"`. Today the field does not pass `required` to the control: pass `required` (or `aria-required`) to the control yourself.
- The message is not a live region: an error that appears is not announced.
- The child must be one element that passes `id` and `aria-*` on to its native control — `Input`, `Select`, `Textarea`, `Checkbox` and `Switch` do. A control wrapped in a `<div>` gets nothing: the `id` lands on the div and the label points at it.
- Today: `Checkbox` and `Switch` have no `invalid` prop. With `error`, the field still passes `invalid` to them, and React warns about an unknown attribute.
- Other `<div>` attributes (`className`, `style`, `data-*`, …) and the `ref` reach the container.

The field has no keys of its own; the control keeps its native keyboard model (see its page).

| key | does |
| --- | --- |
| `tab` / `shift+tab` | Moves focus to / from the control. The label and the messages are not focusable. |
