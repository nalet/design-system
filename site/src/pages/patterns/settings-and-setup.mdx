# settings and setup

where configuration lives. there are four kinds of settings, and each is edited where it is owned. an app's own setup is found from three places and edited in one: the app.

## four kinds of settings

| kind | for example | edited in | owned by |
| --- | --- | --- | --- |
| personal preferences | language, theme | the user menu → preferences (**planned**) | the shell |
| platform settings | people, apps, spaces, tiles | settings | the shell |
| an app's install values | its database address, its resources, the network it uses | settings → addons → values; the platform applies them and may restart the app | the platform, from the schema the app ships |
| an app's own configuration | its connections, sources, policies, schedules | the app's setup views | the app: the shell never stores, receives or draws these values |

an addon owns its configuration. the shell shows whether an app is configured and links to its forms; it never holds the app's settings itself.

## rules

- **one form per section**, and a section's link lands on that form, never on a landing page.
- **summaries count and name; they never quote values**: `2 download clients, 1 unreachable`, not the address of either.
- **secrets are write-only.** a secret shows that it is stored, and offers to replace or clear it — never its value.
- **each form has a save, with an unsaved-changes state** — see [forms and settings](/design-system/patterns/forms-and-settings/). the checklist reflects a save the next time it is read.

## content

- **states** — `ready`, `needs setup`, `degraded`: the app's own words, mapped once onto success, warning and error — see [status vocabulary](/design-system/patterns/status-vocabulary/).
- **summaries** — counts and names: `no search source yet · 2 download clients, 1 unreachable`.
- **the action** — `configure`, on every row and in the strip.
- **the strip** — what is missing and that the app can't work without it: `2 things to set up before it can work: search sources and clients.`

  </Dont>
</DoDont>

- **don't mix setup views into daily work.** setup sits in its own group, at the bottom of the app's navigation.
- **don't report "configured" while one of the app's components is down.** whether it runs is the platform's view; whether it is configured is the app's.
