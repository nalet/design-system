# interaction

Every component answers a person the same way: the same states look the same, focus is always visible and goes where it is expected, and the keyboard works the same everywhere. The component pages say what is particular to each; this page is what they share.

## states

| state | how it shows | where |
| --- | --- | --- |
| Hover | A step brighter: `--surface-2`, and a `--cloud-blue` border on a default button | Buttons, icon buttons, table rows, tiles, menu items |
| Pressed | A step deeper: `--bg-2`, a darker blue on a primary button | Buttons and icon buttons |
| Keyboard focus | A 2px `--focus-ring` outline | Every control: see [focus](#focus) |
| Selected or current | `--surface-selected` with a 2px `--cloud-blue` rule on the leading edge; a blue underline on the current tab; a filled box | Table rows, tabs, filter tabs, tiles, checkboxes |
| Open | The caret turns; `aria-expanded` is set | Message strip details, multi select, table groups, menus |
| Busy | A spinner in the control, or a running rule over a list; `aria-busy` is set | Buttons, menu triggers, the data table |
| Invalid | A `--state-error` border, and the error in words under the field | Inputs, selects, textareas |
| Disabled | Dimmed to 40–50%, a not-allowed cursor, out of the tab order | Every control |

- **Never colour alone.** A selected row also has a checked box; an invalid field also has its error text; the current tab also has its underline.
- **A disabled control can't explain itself.** It can't be focused, so a keyboard or screen-reader user may never find it. When the reason matters ("nothing selected"), say it next to the control, or keep it enabled and explain on press — see [forms and settings](/design-system/patterns/forms-and-settings/).
- **Busy keeps its size.** A button that is loading keeps its width; a list that is refreshing keeps its rows in place under the running rule.

## focus

Buttons, icon buttons, tabs, filter tabs, checkboxes, switches, sort headers and disclosures show a 2px `--focus-ring` outline on keyboard focus (`:focus-visible`) — at least 6:1 against every background; a focused menu item shows a 2px `--focus-ring` bar on its leading edge and a fill. Table rows draw the same ring on their cells, because outlines on table rows are unreliable.

Today: two older families differ. Text fields, selects and textareas show focus as a `--cloud-blue` border with an inset shadow, and launchpad tiles as a `--cloud-blue` frame.

### where focus goes

- **It is never moved without a reason.** Toasts never take it, live updates never steal it.
- **It comes back.** A menu or a dialog gives focus back to what opened it.
- **It stays put** when the control that had it goes away: after "clear" or a bulk action, the selection toolbar holds focus; when a focused row leaves the list, the table's tab stop takes it.
- **It goes to the problem.** After a save that found errors, to the first invalid field — see [forms and settings](/design-system/patterns/forms-and-settings/).

## the keyboard model

- **Everything is reachable and operable without a pointer.** Native elements are used where they exist: buttons, checkboxes, selects, `<details>`.
- **`tab` moves between components; the arrow keys move inside one.** A composite widget takes one tab stop, and the arrows move within it.
- **`enter` and `space` act**, as the browser does for its own controls.
- **`esc` closes the innermost open thing** and gives focus back to its trigger: an open menu in a dialog takes the first `esc`, the dialog the next.
- **Dialogs keep `tab` inside** until they close.

| widget | one tab stop, then |
| --- | --- |
| <C slug="tabs">Tabs</C>, <C slug="filter-tabs" /> | `←` / `→` move and select, `home` / `end` |
| <C slug="toolbar">Toolbar</C> | `←` / `→` between its controls, wrapping around; `home` / `end` |
| <C slug="data-table">Data table</C> | `↑` / `↓` by row, `home` / `end`, `page up` / `page down`; `←` / `→` collapse and expand groups; `tab` goes into the focused row's controls |
| [Launchpad](/design-system/patterns/launchpad-and-tiles/) and <C slug="tile-group">tile groups</C> | A 2-D grid: `→` / `←` in reading order, `↓` / `↑` by position on screen; `home` / `end` |
| <C slug="action-menu">Action menu</C> | Opens on `enter`, `space` or `↓` (`↑` opens it on its last item); the arrows move; `esc` closes |

Each component's exact keys are in the keyboard table on its React page. For text, keys are shown with <C slug="kbd" />: <Kbd>ctrl</Kbd> <Kbd>a</Kbd>.

## selection

Selection works the same wherever rows can be selected: a checkbox per row, `space` to toggle the focused row, `shift` for a range, `ctrl` / `cmd` + `a` for every visible row, and one emphasized action for the whole selection in the toolbar above. A row press opens the row; the checkbox selects it — one click target never does both. The whole model is [selection and bulk actions](/design-system/patterns/selection-and-bulk-actions/).

## pointer and touch

- **Targets are at least 24px** (WCAG 2.5.8). The smallest controls, `sm`, are 28px high; a checkbox's or a switch's whole label is its target, and so is a whole tile.
- **Hover is never the only way in.** What a pointer finds on hover, the keyboard finds on focus: tooltips, a tile's chevron.
- **Nothing depends on a gesture.** No swipe, drag or long press is the only way to do something.
