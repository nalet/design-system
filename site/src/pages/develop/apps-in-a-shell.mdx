# apps in a shell

the portal is a shell: it owns sign-in, navigation, search, notifications and settings, and the apps run inside it as federated modules, in the shell's react tree. the shell also owns the design system. it loads one copy, and every app uses that copy, so a page never carries two versions of it.

## one copy, from the shell

- **the shell loads the design system once**: the package and its `styles.css`, near its root, and one `<Toaster />`.
- **an app shares it, and doesn't bundle it.** the app lists `@nalet/design-system` as a peer dependency, with `react` and `react-dom`, and its federation config shares all three as singletons. at run time the app gets the shell's copy.
- **an app doesn't import `styles.css` in the module the shell loads.** it imports the stylesheet only in its own standalone entry, the one used to run the app on its own.

```js
// in the shell's federation config and in every app's
shared: {
  react: { singleton: true },
  'react-dom': { singleton: true },
  '@nalet/design-system': { singleton: true, requiredVersion: '^0.3.0' },
},
```

## why one copy

two copies of the design system on one page:

- **look different.** two stylesheets define the same class names; whichever loads last wins, for every app on the page, and a component from the older copy is drawn with the newer one's css.
- **lose toasts.** the toast store belongs to one copy of the library. a `toast()` from an app's own copy shows only in a `<Toaster />` of that same copy, not in the shell's.
- **cost twice.** each copy is downloaded, parsed and kept in memory.

## inside the shell

the components are made to live in another app's tree:

- react is a peer dependency, so the shell's single copy of react is used.
- the modal and the action menu render into `document.body` through a portal, so no panel or table of the shell can clip them; toasts are fixed to the viewport.
- nothing is global beyond the tokens and the page base, and there is no provider to set up.
- give a worklist or a form `headingLevel={2}` when the shell owns the page's `h1`.

## versions

- the shell pins one version of the design system, and every app runs on it.
- an app declares the range it was built and tested against (`requiredVersion`, and its peer dependency). while the system is 0.x, a minor version may change how components look: when the shell moves to a new minor, apps check its [changelog](/design-system/get-started/versioning/).
- an app that needs a newer version waits for the shell to move, rather than bundling the version it wants.

## on its own

outside the shell — running the app on its own, in tests — the app loads the design system itself: the install, the stylesheet and the fonts, as on [react](/design-system/develop/react/).

today:

- the package ships no federation config; the shell and the apps declare the shared modules in their own builds.
- nothing warns when two copies end up on one page. check the network panel for a second `styles.css`, or a second copy of the package in the app's bundle.
