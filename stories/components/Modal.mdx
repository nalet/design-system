## implementation notes

- `Modal` renders nothing while `open` is `false`.
- Open, it renders into `document.body` (a portal): a fixed, full-viewport wrapper with `role="presentation"` at `z-index: 100`, the backdrop with `aria-hidden="true"`, and the dialog, centred.
- The dialog has `role="dialog"`, `aria-modal="true"` and `tabindex="-1"`.
- `title` renders as an `<h2>` that names the dialog through `aria-labelledby`. Without a `title`, `ariaLabel` names it through `aria-label`.
- Give it one or the other: with neither, the dialog has no name, and a screen reader can't say what it is about.
- `width` sets the dialog's max width in px, 480 by default.
- `className` lands on the dialog element.
- The header's close button is a `<button type="button">` with `aria-label="close"`.
- `esc`, a click on the backdrop and the close button all call `onClose`.
- The modal never closes itself: you set `open` to `false`.
- When it opens, it remembers the element that has focus and sets `overflow: hidden` on `<body>`, so the page behind doesn't scroll.
- Then it focuses the first `button`, `[href]`, `input`, `select`, `textarea` or `[tabindex]` (other than `-1`) in the dialog, or the dialog itself.
- When it closes, `<body>` gets its earlier `overflow` back, and focus returns to the element it remembered, so people carry on where they were.
- While it is open, the modal listens for keys on the whole document, so they work wherever focus is.
- It takes `esc` in the bubble phase, after the dialog's own widgets, and only when none of them has called `preventDefault()` on it. Then it stops the key, so it goes no further.
- `onClose` may be an inline function. The modal calls the latest one, and runs its open steps only when `open` (or `closeOnEsc`) changes. So a parent that re-renders, such as a list that polls or a field someone types in, doesn't pull focus back to the start.
- A form in the body can submit from the footer: give the `<form>` an `id`, and give the footer button `type="submit"` and `form={id}`. `enter` in a field then submits the form.
- The page behind is not made `inert` or `aria-hidden`. `aria-modal` and the tab trap are what keep people in the dialog.
- `Modal` passes no other attributes through.
- Today: `autoFocus` on a field is overridden, because focus always starts on the first focusable element.
- Today: the dialog takes no `aria-describedby`, because `Modal` passes no other attributes to it.
- Today: the tab trap counts hidden elements, `<input type="hidden">` included. When one is the first or the last focusable match in the dialog, `tab` can leave it.

| key | does |
| --- | --- |
| `tab` / `shift+tab` | Moves through the dialog in the usual order. From its last focusable element it wraps to the first, and back, so focus stays in the dialog (with the limit in the notes above). |
| `esc` | Calls `onClose`, unless `closeOnEsc={false}`. Widgets inside the dialog get it first: an open [action menu](?path=/docs/components-actions-action-menu--docs) closes on the first press, the dialog on the next. Once the dialog takes the key, it goes no further. |
| `enter` / `space` | Native: activates the focused button. `enter` in a field submits its form. |
