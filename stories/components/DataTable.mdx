## implementation notes

### the table

- It renders a `table` in a `div` frame.
- The table is a `grid`, and becomes a `treegrid` once rows are grouped.
- Every feature is a prop, and each one stays off until you pass it.
- The table carries `aria-rowcount`, which counts the header and every row, past the growing limit too, but not the rows inside collapsed groups. So a screen reader can say how many rows there are, including those not shown yet.
- It also carries `aria-colcount`, `aria-multiselectable` when `selectable`, and `aria-busy` while `loading`.
- Rows carry `aria-rowindex`, and `aria-selected` when the table is selectable.
- A row that can't be selected carries no `aria-selected`. Its disabled checkbox says it can't be selected.
- Column headers are `th scope="col"`. The row header, which is the first column or the one with `rowHeader`, is a `th scope="row"`, so it names the row for every other cell in it.
- Name the table: pass `aria-labelledby` with the ID of the heading above it, or `aria-label`.
- `DataTable` takes no other attributes and no `ref`. `aria-label` and `aria-labelledby` go to the `table`, and `className` goes to the frame.
- axe-core finds no violations in this component's stories (WCAG 2.x A and AA, best practice, colour contrast included).

### columns

Each column is an object with these fields:

| field | does |
| --- | --- |
| `id` | Unique. It is the sort's `columnId` and the React key. |
| `header` | The header, any node. CSS lowercases it. An actions column gets a visually hidden one: `<span className="nc-sr-only">actions</span>`. |
| `cell` | `(row) => node`: the cell's content. |
| `sortValue` | `(row) => value`: a string, number, date, boolean or nothing. It makes the column sortable by that value. |
| `compare` | `(a, b) => number`: the other way to make the column sortable, with a full comparator. It wins over `sortValue`. |
| `firstSortDirection` | The direction of the first click: `ascending` (default) or `descending`. Dates usually want `descending`. |
| `align` | `left` (default), `right` or `center`, for the header and the cells. |
| `width` | A width for the column, a number of px or a CSS length, set on its header. |
| `importance` | `high` (the default), `medium` or `low`. See pop-in. |
| `popinLabel` | The label a popped-in value carries. Default: the header when it is a string, otherwise the `id`. |
| `rowHeader` | This column's cell names the row (`th scope="row"`). Default: the first column. |

### sorting

- Sorting is controlled: pass `sort` (`{ columnId, direction }`, or `null`) and `onSortChange`.
- A column is sortable when it has `sortValue` or `compare`, and only while `onSortChange` is there.
- The table sorts `rows` itself.
- Empty values are `null`, `undefined` and `''`. A `compare` function decides everything itself, empty values included.
- With `manualSort`, `rows` arrive already sorted, by a server for instance, and the table only shows the state.
- Today: under `manualSort`, every column's header becomes a sort button, an actions column included. There is no way to leave one out.
- `aria-sort` sits only on the sorted column's header, as `ascending` or `descending`. The other headers carry none.
- `sort` without `onSortChange` is a fixed order: the rows are sorted and `aria-sort` says so, but the header has no button.
- Today: a fixed order has no glyph in the header either, so the order is not shown on screen.

### selection

- `selectable` adds the checkbox column.
- Selection is controlled: `selected` is a set of `rowKey` values, and `onSelectionChange` receives the next set. Without `onSelectionChange`, nothing can change it.
- When `isRowSelectable` returns `false`, the row's checkbox is disabled, and the row stays out of every way of selecting.
- `rowLabel` names each checkbox, so people can tell which row they select: `rowLabel={(r) => r.code}` gives “select S04E07”. Without it, every checkbox is named “select row”.
- The header checkbox's mixed state counts every key in `selected`, including keys of rows that are no longer in `rows`.
- Whether a selection outlives a filter or a tab is up to your app. See [keeping a selection](https://nalet.github.io/design-system/patterns/selection-and-bulk-actions/#keeping-a-selection).

### grouping

- `groupBy` returns a key for each row. Rows that share a key go under one group row, and the table becomes a `treegrid`.
- Group rows sit at `aria-level` 1, with `aria-expanded`, `aria-posinset` and `aria-setsize`. Data rows sit at level 2, numbered within their group.
- `groupHeader(group)` is the group row's label, where `group` is `{ key, rows }`. The default is `key · count`, so pass one when the keys are not words.
- `groupAction(group)` adds one action at the end of the group row.
- The rows of a collapsed group leave the DOM.
- The table can keep the collapsed groups itself, with `defaultCollapsedGroups` setting the start. Or you keep them: pass `collapsedGroups` with `onCollapsedGroupsChange`, for instance to keep them in the URL.
- `onCollapsedGroupsChange` fires either way.

### growing

- `growing={100}` shows the first 100 data rows. Without `growing`, every row renders.
- The count is a polite live region (`aria-live="polite"`), so a screen reader announces each new count when it has a pause.
- `formatGrowing(shown, total)` changes the count's words, and only the count: “show n more” stays as it is.
- The limit only grows, and `growingResetKey` starts it over: a change of its value goes back to one page.
- Pass a string or a number that changes with the filters, such as ``growingResetKey={`${tab}|${query}`}``. An object made on every render would reset it on every render.

### pop-in

- `importance` goes by the table's own width, not the window's. A `ResizeObserver` on the frame measures it.
- Until the table has been measured, and wherever there is no `ResizeObserver`, every column shows.

### row press and highlight

- `onRowPress(row)` makes the row itself an action.
- A click outside the row's controls, with `shift` or without, calls it, and so does `enter` on the focused row.
- `rowHighlight(row)` returns a state (`error`, `warning`, `information`, `success`, `neutral`) or nothing.

### sticky header

- `stickyHeader` is on by default: the header cells stick to the top of the nearest scrolling ancestor.
- The frame has no overflow on purpose, because a frame that scrolled would stop the header from sticking to the page.
- Under something else that sticks, offset the header with `--nc-dt-sticky-top` on any ancestor. The [worklist](?path=/docs/patterns-worklist--docs) sets it to its toolbar's measured height.

```tsx
<div style={{ '--nc-dt-sticky-top': '45px' } as React.CSSProperties}>
  <DataTable aria-label="missing episodes" columns={columns} rows={rows} rowKey={(r) => r.id} />
</div>
```

### loading and empty

- `loading` sets `aria-busy="true"` on the `table` and runs a 2px busy rule along the frame's top edge.
- Under `prefers-reduced-motion`, the busy rule is still and runs the full width.
- `loading` doesn't dim the rows, so people can keep working with them.
- When there are no rows, `empty` renders in the body, in one cell across every column.
- Give it an empty state at `size="sm"`, with a `headingLevel` that fits the page around it.
- A table given `empty` shows it whenever it has no rows, even while `loading`, so pass `empty` only once the load has finished.

### focus and keys

- One row is in the tab order, so `tab` reaches the table in one stop instead of stopping at every row.
- The controls inside every other row (buttons, links, inputs, selects, textareas, summaries and anything with a `tabindex`) are taken out of the tab order with `tabindex="-1"`. They get their own back when their row becomes the tab stop.
- The focus ring is drawn inside the cells, on `:focus-visible` only, because outlines on table rows are unreliable.

On any focused row, a data row or a group row:

| key | does |
| --- | --- |
| `↓` / `↑` | Moves to the next / previous row, group rows included. Stops at the first and the last. |
| `home` / `end` | Moves to the first / last row on screen. |
| `page down` / `page up` | Moves 10 rows down / up. |
| `tab` | Enters the focused row's own controls, then leaves the table. |

On a data row:

| key | does |
| --- | --- |
| `space` | Toggles the row's selection (with `selectable`). |
| `shift+space` | Toggles the row, and sets every row from the last one toggled to this one the same way. |
| `shift+↓` / `shift+↑` | Moves, and selects every row from the last one toggled (or this one) to the row focus lands on. It only adds rows: going back up doesn't clear them. |
| `ctrl+a` / `cmd+a` | Selects every visible row that can be selected. It only adds, and never clears. |
| `enter` | Calls `onRowPress`. Without it, nothing happens. |
| `←` | When grouped, moves to the row's group row. |

On a group row:

| key | does |
| --- | --- |
| `←` | Collapses the group. |
| `→` | Expands it. |
| `enter` / `space` | Toggles it. |

While a control inside a row has focus, the keys go to that control. The arrow keys work from the row itself, so press `shift+tab` to go back to it.

## performance

These numbers come from headless Chromium, on this Storybook's build:

- **3,000 grouped rows, every one rendered** (the [3,000-row story](?path=/story/components-data-display-data-table--three-thousand-rows)): the first render is one task of about 200 ms. Scrolling runs at a median of 16.6 ms per frame (p95 about 23 ms). Toggling one row takes 23–58 ms, select-all about 115 ms, and a sort of every row about 180–265 ms.
- **The same table with `growing={100}`**: every interaction measured (toggle, select all, sort, collapse and show more) takes 5–35 ms, with no long tasks.

The table doesn't virtualise: every row it shows is a row in the DOM. So a few habits keep it quick:

- **Pass `growing` for long lists.** 100 is the page size measured above. Pair it with `growingResetKey`, so a new filter starts again at the first page.
- **Make `columns` once**, at module scope or in `useMemo`. A row's cells re-render only when its row object or the columns change, so a new `columns` array on every render re-renders every row.
- **Keep row objects stable.** Replace only the rows that changed, `rows.map((r) => (r.id === id ? { ...r, state } : r))`, so the others keep their identity and don't re-render.
- **Keep the per-row functions cheap.** `rowLabel`, `isRowSelectable` and `rowHighlight` run for every shown row on every render.
